## 1. 产品定位与完成定义

ArchSync 是一个 Local-first、无需 AI 即可工作的软件架构理解和开发进度监控工具。

用户通过 Windows 客户端添加真实代码仓库，程序自动扫描目录、源文件、函数、接口及静态依赖，构建可探索的架构视图，并使用 Git 与 GitHub 证据追踪变化。

核心闭环：

**打开客户端 → 添加仓库 → 本地自动扫描 → 架构钻取 → 查看真实代码证据 → 持续监控代码变化 → 对比规划与实际 → 关联 GitHub 进度。**

RC5 必须能够在完全关闭 LLM、没有 Agent 插件、没有 GitHub Token 的情况下，对本地 TS/JS/Python 仓库完成真实代码扫描和架构展示。

GitHub 联网仅负责远端协作和 Git 信息，不承担本地源码解析。

### 1.1 产品成功条件

- 本地扫描结果来自实际文件，而非预制 YAML。
- 用户能够从系统节点一直进入真实函数或接口定义。
- 每个函数或接口都能定位到本地文件和源码范围。
- 未知依赖不伪装为已确认调用。
- 不需要预先手写 `.archsync/project.yaml`。
- 不需要 Node.js、Python、pnpm 或 VSCode 才能运行桌面客户端。
- 远端同步异常不能阻止本地架构扫描。
- UI 清楚区分本地事实、GitHub 事实、人工规划和演示数据。

## 3. P0 — 四级真实代码架构模型

### 3.1 层级定义

采用固定的四级主层次：

**Level 1：系统 / 工作区**

用于组织整个仓库或 Monorepo 的应用、服务、内部包与子系统。

例如：

`ArchSync → Web / Server / Scanner / Graph / Config`

系统分组优先使用真实工作区元数据、目录边界和包声明；识别不到时使用确定性目录分组，标记为自动推断。

不得把推断出的业务名称伪装成代码事实。

**Level 2：模块**

模块是逻辑代码单元，可以来自 package、目录、Python package 或经过验证的用户规则。

每个模块必须包含：

- 模块 ID 和显示名称
- 真实源码目录与匹配规则
- 源文件数量
- 类、函数、接口数量
- 上下游依赖
- 本地 HEAD 与扫描时间
- 规划/实际匹配状态
- 识别来源与置信度

**Level 3：文件**

显示文件路径、语言、大小、源代码版本、声明符号和静态引用。

支持从模块节点展开文件列表，点击文件进入符号详情。

**Level 4：代码符号 / 函数 / 接口**

包括函数、方法、类、构造函数、TypeScript interface、类型定义、Python class、Python async function，以及可识别的 HTTP 路由入口。

类的方法可以在符号列表内部形成父子树，不额外增加一个必须展开的全局图层。

### 3.2 代码符号最小数据契约

每个符号必须包含：

- `symbolUid`：持久化分配的不透明稳定身份，用于历史关联和用户标注，不得仅依赖路径、名称或行号。
- `symbolKey`：由当前项目、语言、规范化路径、限定名称、类型及必要的重载区分信息计算的定位键。
- 身份延续及匹配依据遵守第 20 节；原 `symbolId` 表述由双身份契约取代。
- `projectId`、`moduleId`、`filePath`
- `language`
- `kind`：function / method / class / interface / type / constructor / endpoint 等
- `name`、`qualifiedName`
- `signature`
- `parameters`
- `returnType`（未知允许为空）
- `exported` / `visibility`
- `startLine`、`endLine`、必要时包含列号
- `parentSymbolUid`（适用时，引用父符号的稳定身份）
- `decorators` / `modifiers`（适用时）
- `docComment` 或 docstring（原始代码中确实存在时）
- `sourceHash`、`parserVersion`、`scannedAt`
- `analysisStatus`：resolved / partial / unsupported / failed；分析解析状态不替代第 21 节的文件索引状态
- `evidence`：源文件和具体定义位置

不得凭 LLM 或名称猜测填充参数、返回类型、导出状态。

### 3.3 真实代码定位

点击任何实际识别的符号，必须能执行：

**定位文件 → 高亮定义行 → 查看函数签名 → 查看实际源码 → 查看静态引用或调用关系。**

代码查看器默认只读。

源码从用户本地目录读取，不自动上传到服务器或 LLM。

文件已变化时需要提示快照过时，并允许重新扫描。

如果文件被删除，应保留历史证据，但不能假装文件仍存在。

## 4. P0 — TS/JS 自动静态扫描器

### 4.1 技术要求

优先使用 TypeScript Compiler API 或可靠的 AST 解析器，替换目前仅使用正则提取 import 的核心解析方式。

支持：

- TypeScript / TSX
- JavaScript / JSX
- `.mjs` / `.cjs`
- ESM import / export
- CommonJS require
- 动态 import 的静态字符串形式
- 相对路径解析
- `tsconfig` paths / baseUrl
- Monorepo workspace package 引用
- 函数声明和函数表达式
- 箭头函数
- 类与方法
- interface / type alias
- 导出与重导出
- 常见 React 组件
- 常见 Fastify / Express 路由绑定

对无法静态确认的动态表达式标记 unresolved，不能编造解析结果。

### 4.2 静态调用关系

第一版应识别语法层面可定位的函数调用，例如：

- 同文件函数调用
- 经 import 解析的跨文件函数调用
- 可静态确定的类方法引用
- REST 路由到 Handler 的明确绑定

动态分派、反射、复杂运行时依赖注入以及无法证明目标的回调调用，不应声明已验证。

跨前后端 API 关联只有在请求路径、方法及路由匹配可靠时才能生成已解析边。

## 5. P0 — Python 自动静态扫描器

### 5.1 运行时约束

桌面安装包**不得要求用户另外安装 Python 解释器**。

优先采用可随 Node/Electron 分发的 Python 语法解析器，例如 Tree-sitter Python；如选择 Python 标准库 `ast`，则必须提供经过验证的独立解析运行时及安全打包方案。

### 5.2 支持范围

- `.py` 文件
- module 和 package
- `def` / `async def`
- class、method、staticmethod、classmethod
- 参数、默认值、类型标注和返回类型标注
- decorator
- docstring
- import / from-import / relative import
- `__init__.py` 包结构
- 能静态识别的函数调用
- FastAPI / Flask 常见路由声明
- 能静态提取的 HTTP method 与 path

不能静态解析的动态 import、monkey patch、动态属性访问和反射调用，需要记录限制。

### 5.3 Python 验收案例

使用包含 package、子模块、class、async function、decorator、FastAPI route 的固定测试仓库。

核对实际 AST 提取结果与预定义基准，包括符号数量、文件路径、定义范围、签名和可解析引用。

不能只验证“扫描未报错”。

## 6. P0 — 自动模块发现与规划分离

### 6.1 无 YAML 时的行为

用户添加一个无 `.archsync` 配置的仓库：

1. 立即执行只读源码扫描。
2. 自动分析项目类型、目录、包和 import 关系。
3. 自动生成系统与模块建议。
4. 显示真实源文件与符号。
5. 提供用户调整分组的界面。
6. 将扫描索引与个人工作台偏好保存到 ArchSync 用户数据目录。

**默认不必先向仓库写入 YAML 才能查看架构。**

需要导出或提交团队架构配置时，再由用户明确确认是否生成 `.archsync/project.yaml`。

### 6.2 已有 YAML 时的行为

同时维护两套模型：

- **Planned Architecture**：YAML 或用户主动声明的目标架构。
- **Observed Architecture**：从真实源码扫描得到的当前架构。

支持三种差异：

- 规划存在，源码未发现。
- 源码存在，规划未声明。
- 规划与源码匹配。

计划中的模块不应因未识别到文件就被判定为不存在；也不能把模块配置本身当作已检测到代码的证据。

### 6.3 模块自动分组策略

优先级为：

明确 package/workspace 边界 → 可解析的源码目录结构 → 用户配置规则 → 保守的自动建议。

每个分组保存其规则与来源。

允许手动合并、拆分、重命名模块；调整分组不应改变底层符号的文件事实和源码引用。

## 7. P0 — 依赖与调用关系证据模型

区分以下关系类型：

| 关系 | 证据 |
|---|---|
| `contains` | 系统、模块、文件与符号的归属 |
| `imports` | 文件级静态导入 |
| `calls` | 可解析调用表达式 |
| `exports` | 源码导出声明 |
| `implements` | 可静态识别的接口实现 |
| `routes_to` | HTTP route 与 handler |
| `planned_depends_on` | 人工架构配置 |
| `unresolved_reference` | 发现引用但目标不确定 |

所有关系均需带源文件、源码位置、解析状态及分析版本。

建议统一三类证据强度：

- **Observed**：源代码中确实存在该语法事实。
- **Resolved**：静态解析器能够进一步确认引用目标。
- **Inferred**：基于路径和启发式规则推断，尚不能确认。

不得将 Inferred 的调用关系涂成已验证的依赖边。

## 8. P0 — 增量扫描与索引持久化

### 8.1 扫描流水线

文件发现 → 内容哈希 → 语言识别 → AST 解析 → 符号索引 → 依赖解析 → 模块投影 → UI 快照。

首次扫描后保存索引。

文件发生变化时：

- 只重新解析变化文件及必要的受影响引用。
- 删除失效符号和关系。
- 重新绑定变化的定义位置。
- 保留上次成功快照以供故障恢复。
- 不因为某个文件解析失败而把整个仓库清空。

缓存键包含源码内容哈希、解析器版本和必要配置版本。

文件是索引提交的最小原子单位；失败、删除、历史缓存和统计必须遵守第 21 节。

### 8.2 扫描安全

- 不执行被扫描仓库中的程序。
- 不自动执行 npm/pip install。
- 不运行任意 postinstall、构建脚本或项目命令。
- 默认尊重 `.gitignore` 和 ArchSync 忽略规则。
- 不进入 node_modules、虚拟环境、构建输出等不必要目录。
- 不跟随可能逃逸仓库根目录的符号链接。
- 对二进制、大文件、超时、权限失败设置明确处理策略。
- 读取源码仅用于本地解析，不自动发送给 GitHub 或 AI 服务。

### 8.3 性能门禁

在明确记录环境配置的 Windows CI 上，设置初步参考预算：

- 约 1000 个 TS/JS/Python 源文件的测试仓库，首次扫描目标不超过 30 秒。
- 小型变更保存后，目标 5 秒内更新可见结果。
- 大量符号使用列表虚拟化和按需图展开，不一次渲染全部节点。
- 在 1 万个符号的压力数据下，常规搜索与切换不应使界面长期无响应。

具体性能结论必须遵守第 22 节的固定环境、版本锁定数据集、至少 10 次有效测量与原始记录要求。扫描和 UI 分开统计；无固定硬件时仅作为观察性 Benchmark，不宣称达标。

## 9. P0 — 首次启动与仓库接入体验

### 9.1 首次启动

没有用户注册项目时展示欢迎页：

**欢迎使用 ArchSync**

主要操作：

- 打开本地项目
- 克隆 GitHub 仓库
- 添加 GitHub 远端监控
- 查看示例项目

示例必须明确标记为 Demo。

不能默认把安装包内置 `.archsync/project.yaml` 展示为真实源码扫描成功。

### 9.2 再次启动

已有注册项目时进入项目总览，恢复最近使用的项目。

若项目路径失效，展示“仓库路径不可访问”，提供重新定位目录入口。

不要悄悄切换成内置演示项目。

### 9.3 本地 GitHub 仓库

对已经 Clone 的项目：

- 识别本地 HEAD、分支与未提交修改。
- 检查 Git remote。
- 本地源码扫描独立运行。
- GitHub API 同步可单独执行。
- 支持手动 Fetch 更新远端引用。
- **默认不自动 Pull 或 Merge。**

没有 GitHub 授权或网络时，必须仍能进行离线源码扫描。

### 9.4 仅远端监控

GitHub URL 远端只读模式显示 PR、Issue、Commit、Checks 等公开数据。

没有实际下载与分析源码时：

- 不生成虚假的函数级架构。
- 明确显示“远端代码未扫描”。
- 提供克隆并分析的后续入口。

## 10. P0 — 联网诊断与状态真实性

### 10.1 状态拆分

必须分别维护：

**本地 Agent**

服务运行、连接状态、端口和最近错误。

**本地扫描**

仓库路径、扫描结果、源文件数、解析状态、最后成功扫描时间。

**Git 远端**

Remote URL、当前分支、本地 HEAD、远端 HEAD、Fetch 状态。

**GitHub API**

认证模式、最近成功请求、同步结果、限流、最近错误。

**WebSocket**

实时连接、断线与重连状态。

### 10.2 HTTP 400 的处理

HTTP 400 不等于网络断开。

UI 应在主界面显示简洁摘要，诊断面板显示：

- 请求操作
- HTTP 状态码
- 安全脱敏后的接口路径
- 服务端错误码及消息
- 最近成功同步时间
- 是否保留了可信缓存
- 建议重试或检查的操作
- 可复制的诊断 ID

不得输出 Token、Cookie 或其他凭据。

### 10.3 实时与缓存标记

GitHub 状态至少包括：

- 已同步
- 同步中
- 缓存可用
- 数据过时
- 限流
- 认证失败
- 请求失败
- 未配置

绿色“实时”标记不能仅由历史快照的 `source=live` 决定。

任何同步失败后，页面可以保留最后成功数据，但必须明确显示其时间和 Stale 状态。

## 11. P1 — 统一桌面 UI 设计系统

保留深色专业开发工具风格，重新整理信息架构，而不是单独修改按钮颜色。

### 11.1 布局

采用：

**顶栏：** 产品、当前项目、分支、全局搜索、同步状态、设置。

**左侧：** 项目树与系统/模块/文件/函数导航。

**中央：** 架构图与面包屑层级导航。

**右侧：** 当前选中元素详情、代码预览、依赖与证据。

**底部可折叠区域：** 扫描结果、GitHub 活动、错误诊断、日志。

工作流与实现状态筛选放入专用筛选面板，不再全部堆在顶栏。

视图切换保留一个主入口。

### 11.2 架构钻取

- 默认系统或模块级视图。
- 双击或明确操作进入下一级。
- 面包屑支持返回。
- 文件层显示关键函数摘要。
- 函数层按需展开。
- 可选择只显示公开函数、HTTP 接口、最近变更函数。
- 支持回退上一层与定位当前选中项。
- 图节点、左侧目录和右侧详情始终保持选中状态一致。

### 11.3 统一视觉规范

建立 Design Tokens：

- 基础颜色、语义状态颜色
- 字体字号与层级
- 间距、边框、圆角
- 按钮类型
- 图标规格
- 表格和列表密度
- Hover、Selected、Disabled、Loading、Error 状态

图节点不允许混用多套字体、任意颜色和随意尺寸。

颜色必须表达清晰语义，不能将图层颜色与任务进度颜色混淆。

### 11.4 自适应布局

必须在以下条件测试：

- 1366×768
- 1920×1080
- Windows 125% / 150% 缩放

画布自动 Fit 不应让节点文字小到无法阅读。

当图过大时使用按层级聚合和局部展开，而不是无限缩小整张图。

### 11.5 Windows 桌面一致性

- 修复任务栏与托盘图标。
- 检查打包资源路径和 Windows DPI。
- 处理原生菜单栏与深色主题的不协调。
- 保留用户对窗口大小、布局、侧栏宽度及上次项目的偏好。

## 20. A — 符号身份与重命名、移动的延续规则

### A.1 双身份设计

每个扫描符号同时具有：

- `symbolUid`：由 ArchSync 持久化分配的不透明稳定身份，用于历史关联和用户标注。
- `symbolKey`：根据当前项目、语言、规范化路径、限定名称、符号类型及必要的重载区分信息计算的定位键。

`symbolUid` 不得仅依赖文件路径、函数名称或行号。函数移动、重命名、代码插入导致行号变化时，需要尝试保持同一符号身份，但不能仅凭名称相似就认定为同一符号。

### A.2 身份延续策略

按以下证据优先级匹配：

1. 文件及符号位置不变，且 AST 声明能够明确对应。
2. Git 重命名记录结合 AST 结构、限定名称及上下文匹配。
3. 文件内容哈希及符号结构指纹的唯一匹配。
4. 同一作用域内可通过源码差异定位的声明变化。

只有匹配结果唯一、证据充分时，才能延续旧 `symbolUid`。无法确认时，分配新的 `symbolUid`，保留旧符号历史；可记录 `possiblePredecessor` 候选关系，不自动继承人工验收或历史标注。

### A.3 特殊情况

- 函数仅改变行号：应保持身份。
- 函数重命名但主体保持一致，且匹配唯一：允许保持身份。
- 文件被 Git 重命名，内部符号未变化：应尽量保持身份。
- 一个函数拆分成多个：不得把旧身份同时赋予多个新函数。
- 多个函数合并为一个：不得直接将多个历史身份合并。
- 两个函数高度相似：不确定时保持独立。

每次身份延续必须保存匹配依据和分析版本。

**验收 AC-17：** 对函数移动、重命名、拆分、合并、同名重载及行号变化进行测试，不出现符号 ID 冲突、误继承或历史记录丢失。

## 21. B — 单文件解析失败与 Stale 索引契约

### B.1 原子更新

扫描器以文件为最小原子更新单位。只有某个文件完整解析成功，才可以将其新符号和依赖集合提交为当前可信索引。解析失败不得先清空旧数据，再保存一份空结果。

### B.2 解析失败行为

例如 `service.ts` 原有 8 个已识别函数，用户编辑造成语法错误，新一轮解析失败。系统应：

- 保留此前成功解析的 8 个符号作为历史缓存，将文件标记为 `stale`。
- 显示最新内容哈希与最后成功解析的内容哈希。
- 记录错误类型、位置和时间。
- 不把旧符号算作本次扫描确认的有效函数。
- 不把旧调用关系显示为当前已验证。
- 修复后自动重新解析，并原子替换过期索引。

### B.3 状态类型

统一文件索引状态：

| 状态 | 含义 |
|---|---|
| `fresh` | 当前文件内容解析成功 |
| `partial` | 部分事实可提取，但分析不完整 |
| `stale` | 当前文件解析失败，保留上一次成功结果 |
| `unsupported` | 语言或语法特性暂不支持 |
| `unavailable` | 文件无法读取 |
| `deleted` | 文件已删除，当前符号关系应失效 |

文件删除不得被误判为普通解析失败。

### B.4 UI 与统计要求

分别统计当前成功解析的文件和符号、部分解析文件、过期文件与历史符号、不支持文件、读取或解析失败文件。

默认代码搜索优先显示 Fresh 结果。Stale 结果可供查看，但必须明显标记过期，不得作为当前代码事实参与已确认依赖计算。

**验收 AC-18：** 对语法错误、文件读取失败、修复恢复、删除及批量变更进行测试，确保旧缓存不丢失、不冒充最新数据，恢复后能够正确替换。

## 22. C — 性能测试的固定环境与统计口径

### C.1 基准运行环境

使用可复现的 Windows x64 参考环境，建议 Windows 11 x64 或等价固定环境、8 个逻辑 CPU、16 GB RAM、SSD；固定 Electron、Node、扫描器及依赖版本，关闭 LLM API、禁用 GitHub 网络同步，无外部 Agent 参与。

使用 GitHub-hosted Windows Runner 时，记录实际可见的 CPU、内存、系统版本与执行环境。未经核实不得直接比较不同机器的结果。性能回归强制门禁优先在固定或等价规格的 Runner 执行。

### C.2 固定数据集

至少提供三个版本锁定的数据集：

- **Dataset A：TS/JS 基准项目。** 约 1000 个 TS/JS/TSX 源文件，包含函数、类、接口、模块导入及跨包依赖。
- **Dataset B：Python 基准项目。** 包含 package、class、def、async def、decorator、import 和 API route。
- **Dataset C：混合大型索引。** 约 10000 个符号，覆盖多模块、跨文件引用及图谱交互。

合成数据集使用固定随机种子、固定生成器版本并记录内容哈希。真实开源仓库固定 Commit SHA，不用可变分支 HEAD 作为长期基准。

### C.3 测量项目

分别记录冷启动完整扫描、缓存命中重复扫描、单文件修改增量扫描、单文件删除、文件移动与符号重命名、解析失败和恢复、UI 图谱首次可交互时间、模块/文件/函数切换响应、峰值 RSS 内存、CPU 使用与文件 I/O。

### C.4 统计方式

每个主要性能场景至少进行 10 次有效测量，记录 P50、P95、最小值、最大值、执行环境、数据集版本、代码 Commit SHA 和解析器版本。

冷扫描使用明确的空缓存状态；增量扫描先完成基线索引，两类结果不得混合统计。扫描性能与 UI 渲染性能分别计算。

### C.5 初步目标

在参考环境中：

- 1000 文件完整冷扫描：P95 不超过 30 秒。
- 单文件小幅修改到新索引可用：P95 不超过 5 秒。
- 10000 符号规模下搜索和钻取保持可交互，不将所有符号一次展开成全量图。

无可复现固定硬件条件的 CI，可先作为观察性 Benchmark，不得虚构性能达标结论。

**验收 AC-19：** 提供原始测量记录、机器配置、数据集哈希及可复现命令，不允许仅报告一次最快运行结果。
